# LanternBox Modular Hardware Standard v0.1

## 1. 文档目的

本标准用于统一 LanternBox / 壳中灯全部终端设备的模块化硬件设计。

适用设备包括但不限于：

- FT 系列现场终端
- 学习终端
- 通讯终端
- 导航终端
- 传感器节点
- 车辆终端
- 基地节点
- 后续新增的其他终端

本标准的目标不是单纯提高装配便利性，而是确保在长期缺乏外部供应、专业维修设备和技术支持的情况下，设备仍然能够被维护、替换、拆解、重组和继续使用。

---

## 2. 核心设计原则

### 2.1 功能模块不得永久绑定主控

GNSS、LoRa、键盘、音频、摄像头、存储、传感器、通信、电源管理等可替换能力，不得在没有充分理由的情况下永久焊死在主控板上。

主控板负责：

- 计算
- 调度
- 总线管理
- 电源控制
- 模块识别
- 固件更新
- 安全校验

功能模块负责提供独立能力。

### 2.2 跨终端互换

模块不得只适用于单一终端型号。

同一 GNSS、LoRa、键盘、音频或传感器模块，应尽可能能够在不同类型终端之间直接互换。

互换后不应要求：

- 重新焊接
- 修改主板
- 更换专用线束
- 使用热风枪
- 使用专用烧录器
- 连接外部网络
- 重新编译整个主控固件

### 2.3 普通工具可维修

标准维护操作应尽量只需要：

- 十字螺丝刀
- 一字螺丝刀
- 镊子
- 简单万用表

模块更换流程应接近：

1. 关机
2. 拆下后盖
3. 拔下标准连接器
4. 拆下模块固定螺丝
5. 更换模块
6. 重新装配
7. 开机自动识别

### 2.4 禁止隐性不可维修结构

原则上禁止：

- 永久胶封
- 不可逆卡扣
- 模块间飞线
- 直接焊接排线作为常规连接
- 必须破坏外壳才能拆卸
- 同一接口使用不同电压但无防呆
- 无标签、无方向标识、无版本标识
- 依赖云端或专有软件才能恢复

## 3. 系统分层

LanternBox 终端硬件统一分为三层。

### 3.1 Core Board 主控底板

主控底板提供：

- 主处理器
- 基础内存
- 系统存储
- 电源管理
- 模块插槽
- 调试与恢复接口
- 模块电源开关
- 总线复用与隔离
- 设备身份与安全能力

主控底板应保留足够的：

- GPIO
- UART
- I²C
- SPI
- USB
- CAN
- 中断输入
- 电源控制通道

不得以“当前刚好够用”为目标，应保留明确扩展余量。

### 3.2 Functional Module 功能模块

功能模块包括但不限于：

- GNSS
- LoRa
- 键盘
- 麦克风
- 扬声器 / 音频编解码
- 摄像头
- microSD / 扩展存储
- 环境传感器
- 电池与电源管理
- CAN
- 蜂窝通信
- 短波或其他无线扩展

每个模块应具备：

- 独立功能芯片
- 必要电源与保护电路
- 统一连接器
- 固定孔
- 清晰标签
- 模块身份信息
- 硬件版本号
- 可查询能力描述

### 3.3 Carrier / Enclosure 机械载体

机壳负责：

- 固定模块
- 防护
- 散热
- 防尘
- 天线净空
- 线束管理
- 维护入口

机壳不得让模块直接依赖胶水或压力固定。

模块应安装在标准托架、滑槽或固定柱上。

## 4. 模块尺寸等级

初期定义三类模块，具体尺寸在完成 FT-02 机械验证后冻结。

### Module-S

适用于：

- GNSS
- RTC
- 小型传感器
- 电源检测
- 小型接口转换

要求：

- 低功耗
- 单一主要能力
- 两点固定
- 可快速更换

### Module-M

适用于：

- LoRa
- 音频
- 键盘控制
- 摄像头控制
- 存储
- 复杂传感器

要求：

- 独立电源管理
- 两到四点固定
- 支持中速或高速总线

### Module-L

适用于：

- 高功耗无线模块
- 大型音频模块
- 蜂窝通信
- 独立计算模块
- 大容量电源模块

要求：

- 独立保险或限流
- 明确散热设计
- 独立电源使能
- 必要时使用 CAN 或 USB

模块尺寸等级必须统一：

- PCB外形
- 安装孔位置
- 螺丝规格
- 最大器件高度
- 接口位置
- 天线净空区
- 散热边界

---

## 5. 机械标准

### 5.1 紧固件

优先使用：

- M2
- M2.5

同一终端内部尽量不超过两种螺丝规格。

不得使用难以获得的专用螺丝作为常规紧固件。

### 5.2 固定方式

模块应优先采用：

- 螺柱
- 螺丝
- 标准托架
- 可拆滑轨

不得仅依靠连接器承重。

### 5.3 防呆

模块必须通过至少一种方式防止反插：

- 非对称连接器
- 定位缺口
- 不同孔位
- 明确方向标识
- 机械键位

### 5.4 标签

每个模块必须标注：

- 模块名称
- 模块类型
- 硬件版本
- 电压
- 接口方向
- 关键引脚
- 序列号或模块ID

标签应在拆开机壳后可直接读取。

---

## 6. 电气标准

### 6.1 标准电源轨

优先使用：

- 3.3V
- 5V
- GND

其他电压必须由模块内部转换，不应扩散为系统通用电源。

### 6.2 电源控制

中高功耗模块应支持：

- 独立使能
- 软件断电
- 过流保护
- 上电延时
- 故障隔离

### 6.3 保护要求

模块接口应根据使用场景具备：

- ESD保护
- 反接保护
- 过压保护
- 限流
- 热插拔保护或明确禁止热插拔

### 6.4 电源能力声明

每个模块必须声明：

- 工作电压
- 峰值电流
- 平均电流
- 睡眠电流
- 启动浪涌
- 是否允许热插拔

---

## 7. 通信总线标准

### 7.1 I²C

适用于：

- 键盘
- 低速传感器
- RTC
- 电源管理
- 模块身份读取

要求：

- 统一SDA/SCL定义
- 明确上拉电阻归属
- 模块地址可配置或可识别
- 避免地址冲突
- 长线场景不得直接使用裸I²C

### 7.2 UART

适用于：

- GNSS
- LoRa控制模块
- 语音模块
- 独立控制器

要求：

- 明确主从方向
- 默认波特率
- 电平标准
- 是否支持硬件流控
- 是否支持固件升级

### 7.3 SPI

适用于：

- 墨水屏
- SD卡
- 高速无线模块
- 部分摄像头与存储

要求：

- SCK / MOSI / MISO共享
- 每个模块独立CS
- 高冲突风险模块应支持总线隔离
- 明确最高频率与模式

### 7.4 USB-C

适用于：

- 外接键盘
- 存储
- 维护
- 固件恢复
- 高速扩展

USB-C接口必须明确角色：

- Device
- Host
- Dual-role
- Power only
- Service only

不得仅根据接口外形推断功能。

### 7.5 CAN

适用于：

- 外部传感器
- 车辆节点
- 长线连接
- 高干扰环境
- 分布式模块

CAN模块应支持：

- 可更换收发器
- 终端电阻配置
- 节点ID
- 故障隔离
- 统一消息格式

## 8. 模块身份与能力描述

每个可替换模块应提供可读取身份信息。

最小字段：

```text
module_type
module_id
hardware_revision
firmware_version
serial_number
power_profile
bus_type
capabilities
manufacturer
```

建议通过：

- I²C EEPROM
- 模块控制器内部存储
- 1-Wire身份芯片

实现自动识别。

主控启动时应能够：

1. 扫描模块
2. 读取身份
3. 校验兼容性
4. 加载对应驱动
5. 检查供电需求
6. 显示故障或缺失状态

---

## 9. 软件抽象要求

上层软件不得绑定具体芯片型号。

应通过统一能力接口调用：

```text
GNSS.getPosition()
GNSS.getTime()
Radio.sendMessage()
Radio.receiveMessage()
Keyboard.readKey()
Audio.startRecording()
Audio.play()
Camera.capture()
Storage.write()
```

更换模块后，应尽量只替换底层驱动，不修改业务逻辑。

模块驱动必须声明：

- 支持的硬件版本
- 通信总线
- 初始化方式
- 故障状态
- 功耗状态
- 自检能力

---

## 10. 跨终端兼容规则

模块跨终端互换时，应满足：

- 机械尺寸兼容
- 螺丝孔兼容
- 电压兼容
- 连接器兼容
- 总线兼容
- 身份协议兼容
- 驱动抽象兼容
- 固件可自动加载或预置

不同终端可以拥有不同数量的模块槽，但同等级槽位必须保持一致。

不得出现：

- FT专用GNSS
- 学习终端专用LoRa
- 车辆终端专用键盘接口

除非物理环境确实要求特殊版本，并且特殊版本仍应尽可能保留协议兼容。

---

## 11. 维修与更换标准

每个模块必须具备维护说明，至少包括：

- 拆卸步骤
- 安装步骤
- 所需工具
- 故障表现
- 自检方法
- 替代模块列表
- 接口定义
- 供电参数
- 固件恢复方式

标准更换操作不得超过：

- 拆除后盖
- 拔插一个连接器
- 拆装四颗以内螺丝
- 开机自动识别

---

## 12. 文档与档案要求

每个模块必须配套：

```text
module_name/
├── README.md
├── pinout.md
├── mechanical.md
├── power.md
├── protocol.md
├── firmware.md
├── repair.md
└── compatibility.md
```

必须保存：

- 原理图
- PCB文件
- BOM
- 固件源码
- 引脚定义
- 通信协议
- 机械尺寸图
- 3D模型
- 替代器件信息
- 已验证终端列表

文档必须可离线保存和阅读。

---

## 13. 设计审查清单

任何新模块进入 LanternBox 硬件池前，必须回答：

- 是否可仅用螺丝刀拆装？
- 是否无需焊接即可更换？
- 是否有防呆？
- 是否有清晰标签？
- 是否能自动识别？
- 是否支持跨终端使用？
- 是否声明功耗？
- 是否有替代器件？
- 是否有离线维修文档？
- 是否有自检能力？
- 是否会占用不可替代接口？
- 是否保留未来扩展余量？

任一关键项不满足，不得直接冻结为正式模块。

---

## 14. FT-02 当前适用要求

FT-02 后续设计必须优先模块化以下能力：

- GNSS
- LoRa
- 键盘
- 音频输入
- 音频输出
- 存储
- 摄像头
- CAN
- 电源管理

FT-02 主控建议继续采用具备较大资源余量的 ESP32-S3 N16R8 级别方案，并通过自定义载板提供统一模块接口。

不得仅因某块开发板体积更小，就牺牲：

- GPIO余量
- PSRAM
- Flash容量
- 总线数量
- 模块供电能力
- 后续摄像头与音频扩展能力

---

## 15. 冻结原则

从本标准发布起：

> LanternBox 终端硬件不得将可替换功能模块永久绑定于主控板。GNSS、LoRa、键盘、音频、摄像头、存储及其他扩展功能，应采用统一机械、电气、通信和身份协议，并能够在不同类型终端间互换。标准维护操作应仅需普通手工具完成，不依赖焊接、热风、专用编程设备或外部网络。

本标准作为 FT-02 及后续全部 LanternBox 终端硬件设计的基础约束。

后续所有硬件方案、PCB、机壳、连接器和固件架构，均应接受本标准审查。
